# 이번 라운드에 넣은 최적화들, 그리고 서로 어떻게 물리는지

작성일: 2026-08-21

숫자는 전부 `verification/records/speed.md` 에서 왔다. 이 문서는 그 기록을 요약하지 않는다 —
**무엇을 켰고, 얼마를 벌었고, 어디서 서로 겹치는지**를 한 장에 모으는 것이 목적이다.

두 노드에서 쟀다. 2026-08-20 은 `m7i.12xlarge` 4대(48 vCPU, 185 GB, gp3 1000 MB/s),
2026-08-21 은 `m8i.16xlarge` 1대(64 vCPU, 247 GB, 30 Gb/s NIC, gp3 4-way 스트라이프).

## 전송

| 기법 | 효과 | 왜 |
| --- | --- | --- |
| CRT 클라이언트를 이미지에 심는다 | 323.6 → 676.6 MB/s (**2.1×**) | 설정 자체는 `node.sh` 에 있었다. 드라이버가 `--entrypoint python` 으로 각 단계를 띄워 `node.sh` 가 실행되지 않았고, 런처는 같은 설정을 **호스트** user-data 에 걸었다. 전송은 컨테이너 안에서 돌고 그쪽 `$HOME` 은 다르다. 3.9 TB 가 스톡 기본값으로 옮겨졌다 |
| gp3 4-way 스트라이프 | 676.6 → 1,370.7 MB/s | 볼륨 하나가 16,000 IOPS 에서 막힌다. RLDS 샤드 쓰기가 ~40 KB 라 IOPS 바운드이고, 프로비저닝 MB/s 를 올려도 안 움직인다 |
| `target_bandwidth` 를 NIC 속도로 선언 | 1,330.8 → 2,687.7 MB/s (**2×**) | 같은 기록의 이전 판이 이걸 "3%" 라고 적었다. 그 측정은 단일 gp3 로 677 MB/s 에 묶인 노드에서 쟀다 — 답이 변할 수 없는 자리에서 잰 것 |
| 64 MB 청크 | 유지 | 단조롭지 않다: 16 MB 2,797.4 / 64 MB 2,687.7 / 128 MB 1,877.7. 16 MB 의 4% 는 런 간 편차 안이고 128 MB 는 확실히 나쁘다 |
| **합계** | **447.9 → 2,916.4 MB/s (6.5×)** | 이 인스턴스 NIC 의 78%, 명목 EBS 예산의 117%. 다음 제약은 링크이고, 더 빠른 다운로드는 설정이 아니라 더 큰 인스턴스가 필요하다 |

## 변환 — 병렬성

| 기법 | 효과 | 왜 |
| --- | --- | --- |
| 워커 수를 메모리로 산정 (`worker_budget`) | 48 → 30 (185 GB / 48코어) | 코어당 하나는 226 GB 를 요구했고 커널이 12개를 죽였다. 제약은 코어당 메모리가 아니라 **워커당** 메모리다 |
| 워커 메모리를 에피소드 크기로 모델링 (`worker_memory`) | toto 41 → 22 워커 | 상수 6 GB 는 toto(9.28 GB)와 jaco_play(4.74 GB) 사이, 즉 최악의 자리였다. 4.4 GB base + 에피소드 소스 바이트의 32배, ×1.25 마진 |
| 읽기 경계 (`interleave_cycle_length=1`, `PREFETCH_EPISODES`) | 워커 7.75 GB 의 대부분 | tf.data 의 AUTOTUNE 은 이런 게 22개 동시에 돈다는 걸 모른다. 머신이 찰 때까지 버퍼링한다. 순차 소비자가 쓸 수 있는 건 한 에피소드 앞까지다 |
| 태스크 크기 25 → 8 에피소드 | 1,177 → 1,262 fps, 피크 160.7 → 132.5 GB | 두 축이 **동시에** 개선된 드문 경우. 3까지 내리면 1,158 로 뒤집힌다 — 태스크 설정비가 병렬성보다 커진다 |
| `spawn` 을 프로세스 기본값으로 | 15시간 행 제거 | datatrove 는 `start_method` 를 pool 에만 주고 `Manager()` 에는 안 준다. TF 가 로드된 부모에서 fork 된 Manager 는 소유자 없는 락을 물고 멈추고, 워커는 그 큐에서 블록한다 |

## 변환 — 실패 감지

느려서 잃은 시간보다 **멈춰서** 잃은 시간이 컸다. 4노드 중 3노드가 66~107분씩 load 0.00 이었다.

| 기법 | 효과 | 왜 |
| --- | --- | --- |
| `watch_for_oom` | 10초 안에 exit 76 | OOM 된 워커가 pool 의 태스크 큐 락을 쥔 채 죽으면 나머지 42개가 `Queue.get` 에서, 부모는 `pool.next` 에서 영원히 기다린다. `/proc/vmstat` 의 `oom_kill` 은 root 가 필요 없다 |
| stall watchdog | exit 75 | 어떤 워커 수 추정도 항상 맞지는 않는다는 전제 위에 있다 |
| watchdog 무장 구간을 executor + aggregation 으로 한정 | 오탐 제거 | 무장 해제가 없어서 성공한 빌드의 업로드 중에 터질 수 있었다 — 업로드는 로컬 바이트를 안 쓰고, "20분간 아무것도 안 썼다" 는 정확히 stall watchdog 이 찾는 모양이다. 자기 테스트 스위트도 한 번 죽였다 |

## 오케스트레이션

| 기법 | 효과 | 왜 |
| --- | --- | --- |
| 단계를 겹치지 않는다 | 1.3시간 포기 | 대신 용량 예측, 백프레셔, reclaim 순서 판단이 설계에서 사라진다 — 자동 삭제가 있는 설계에서 그것들은 틀리면 데이터가 없어지는 종류다. 덤으로 전처리 측정이 네트워크 I/O 에 오염되지 않는다 |

## 서로 물리는 지점

### 고쳤다 — 배치 동시성이 메모리 산정을 무효화하고 있었다

`process` 는 배치의 빌드를 **동시에** 띄운다. 각 빌드는 별도 프로세스이고, 그 안의
`worker_budget` 은 `available_memory()` 로 **머신 전체**를 읽는다. 그래서 3개짜리 배치는
185 GB 노드에서 555 GB 를 계획한다 — `worker_budget` 과 `watch_for_oom` 이 막으려고 만들어진
바로 그 과약정이, 그것들이 보지 않는 한 층 위에서 다시 생긴 것이다.

기존 `_worker_share` 가 이걸 반쯤 막고 있었다. ffmpeg 워커 수만 나누고, `runtime.workers` 가
선언돼 있을 때만 동작한다 — 출하되는 `ec2.yaml` 은 `null` 이라 아무것도 하지 않았다.

이제 오케스트레이터가 `ANY4LEROBOT_MEMORY_SHARE` 로 몇 개가 노드를 나눠 쓰는지 선언하고,
`worker_budget` 이 그만큼 나눈다. 시작한 개수를 아는 것은 오케스트레이터뿐이다.

**코어는 일부러 안 나눴다.** 과약정된 CPU 는 성능이 깎이고(워커 수를 고른 그 측정에서 CPU 는
34% 유휴였다), 과약정된 메모리는 깎이지 않고 노드를 멈춘다.

### 문서화했다 — `-1` 이 두 가지를 뜻한다

| 자리 | `-1` | 단위 |
| --- | --- | --- |
| `worker_budget` / `local_config` | 메모리가 담는 만큼 | 에피소드 하나를 통째로 든 **프로세스** |
| `resolve_workers`, `PlannedVideoFiles.build` | 코어당 하나 | ffmpeg/pyarrow 를 기다리는 **스레드** |

둘 다 맞다. 단위가 다르기 때문이다. 문제는 그 규칙이 어디에도 안 적혀 있었다는 것이고,
이런 건 복사될 때 조용히 틀린 쪽을 가져간다. 두 자리에 왜 그런지 적었다.

### 의도된 중복 — 한 실패에 세 겹

읽기 경계(예방) → 메모리 예산(예방) → OOM/stall watchdog(감지). 중복으로 보이지만 아니다.
기록이 명시한다: **어떤 워커 수 추정도 항상 맞지는 않는다.** 하나를 중복이라고 지우면 15시간
행이 돌아온다.

### 손대지 않았다 — 메모리 모델은 높게 편향돼 있고, 그게 공짜다

toto 워커에 11.6 GB 를 배정하는데 실측 피크는 169 GB / 22 = **7.7 GB** 다. 50% 과다 배정이다.
그런데 처리량이 22 → 61 워커에서 평평하다(0.8%). 39개를 더 넣으면 91 GB 와 CPU 여유를 다 쓰고
아무것도 못 번다. **병렬성은 더 이상 제약이 아니다.** 그러니 이 보수성은 처리량을 남기고 있는
것이 아니고, 조이면 위험만 늘어난다.

### 정리했다 — 폐기된 근거가 설정 파일에 남아 있었다

`ec2.yaml` 은 `-1` 을 "코어당 워커 하나" 로 정의한 다음 두 줄 뒤에서 스스로 뒤집고 있었고,
태스크 크기를 두 군데서 서로 다르게(25 / 8) 논증하고 있었다. 틀린 정의를 먼저 읽게 두는 주석은
없는 주석보다 나쁘다.

## 아직 열려 있는 것

- **픽셀 일치.** taco_play 와 stanford_hydra 가 0.976 / 0.977 로 0.98 문턱을 0.3~0.4% 폭으로
  못 넘긴다. 컬렉션에 남은 유일한 영상 차이다.
- **워커 시간의 6/7 이 미계측.** 프레임 루프는 9.2 ms/frame = 워커당 109 fps 인데 30 워커가
  3,300 이 아니라 450 을 낸다. LeRobot writer, 에피소드 단위 부기, 태스크 프로세스 시작,
  집계 — 아무것도 안 재봤다.
- **다운로드는 NIC 의 78%.** 다음 개선은 설정이 아니라 인스턴스다.
